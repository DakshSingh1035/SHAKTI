SHAKTI DESIGN AND WORKFLOWS
============================

This file records the proposed user experience, hardware behaviour, and
communication workflows for the Shakti safety platform.

1. USER EXPERIENCE
------------------

The wearer should be able to activate SOS quickly from either the wristband or
the Android application. The interface should provide:

* A clear manual SOS control.
* Long-press or equivalent protection against accidental activation.
* Immediate local confirmation through vibration and on-screen feedback.
* A visible incident identifier or status reference.
* Precise language such as "saved locally", "server received", or "recipient
  acknowledged" instead of a generic "sent".
* Consent and privacy controls for location, recording, camera warnings, and
  emergency contacts.
* Low-battery and degraded-network explanations.

2. MANUAL WRISTBAND SOS
-----------------------

The intended workflow is:

Button press and hold
  -> debounce and validate
  -> create incident ID
  -> persist incident in non-volatile storage
  -> vibrate immediately
  -> request the best available location
  -> transfer over BLE and/or independent LTE
  -> retry other configured paths if needed
  -> show exact delivery state

If every remote path fails, the wristband must retain the incident and explain
that delivery is pending. Local feedback is still successful even when remote
communication is not.

3. PHONE UNAVAILABLE
--------------------

When the phone is unavailable, the wristband's independent cellular modem may
send the incident using its own SIM/eSIM and GNSS. If terrestrial cellular
service is unavailable, a separately validated satellite accessory may be
attempted. If no path succeeds, the local queue remains authoritative until a
later retry or an explicitly defined closure.

4. NETWORK OUTAGE AND RECOVERY
------------------------------

The Android app and wristband retain pending incidents locally. When a route
returns, queued incidents are retried with backoff. The backend uses the
incident ID for deduplication, so the same emergency can be retried without
creating duplicate incidents.

The product must not say that a contact, control room, or emergency agency was
notified until the corresponding receiver acknowledges the message.

5. NEARBY CAMERA WARNING
------------------------

An authorized camera service can produce a candidate event with:

* Camera identifier and authorization record.
* Event type, time, and confidence.
* Location and coverage geometry.
* Evidence reference where permitted.
* Review status.

The backend can compare the event location and time with opted-in users inside
a configured warning radius. It may send a limited warning to the app and a
vibration to a paired band. Camera events remain candidates until reviewed;
the system must not expose unnecessary camera data or infer identity by
default.

6. EVIDENCE WORKFLOW
--------------------

Where the user has granted permission and policy allows recording:

1. Capture media with device and incident context.
2. Segment media when appropriate.
3. Encrypt locally when feasible and queue securely if offline.
4. Calculate a SHA-256 digest and create metadata.
5. Upload over an authenticated encrypted connection.
6. Verify the digest at the backend.
7. Store media in private, access-controlled object storage.
8. Record access, export, review, and deletion events.
9. Apply retention and controlled-disclosure policy.

A hash detects changes to a file after a digest is recorded. It does not by
itself prove who recorded the file, when it was recorded, or that it is legally
admissible.

7. WRISTBAND HARDWARE DESIGN
----------------------------

The proposed hardware is modular:

* ESP32-class low-power controller.
* BLE radio and secure pairing.
* SOS button and haptic motor.
* Protected Li-Po battery and charging circuit.
* Battery fuel gauge, temperature sensing, and brownout detection.
* Dedicated modem power rail for LTE or satellite peak current.
* GNSS receiver for independent location.
* Optional relay or satellite module.

Power-saving rules include deep sleep, load switches for radios, short haptic
patterns, on-demand GNSS, and modem activation only when required. The modem
rail must be sized for peak transmit current, not average current.

8. BLE INTERFACE CONCEPT
------------------------

An illustrative GATT service may expose:

Device Information
  Firmware version, hardware revision, and device identifier.

Device Status
  Battery, charging state, radio state, and fault flags.

SOS Event
  Incident ID, event type, timestamp, location availability, and sequence.

Command
  Approved app-to-band commands such as acknowledgement display or status
  request.

Haptic Control
  Authorized feedback commands with authenticated access.

All control commands require authenticated pairing and authorization.

9. COMMUNICATION LIMITS
-----------------------

BLE depends on a nearby powered phone. LTE depends on a compatible modem,
operator service, SIM/eSIM, and coverage. GNSS needs sky visibility and may
take time to obtain a fix. LoRa requires a deployed gateway and backhaul.
Satellite requires compatible equipment, subscription, power, antenna, sky
view, and regulatory approval.

These are independent options, not promises of universal coverage.
