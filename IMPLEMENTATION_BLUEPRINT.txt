SHAKTI IMPLEMENTATION BLUEPRINT
================================

This is a proposed engineering plan. The APIs, entities, technologies, and
stages below are design examples, not existing deployed interfaces.

1. PROPOSED TECHNOLOGY
----------------------

Android
  Kotlin and modern Android components for account, permissions, BLE, location,
  notifications, and incident status.

Wristband
  ESP32-class controller, BLE, persistent storage, haptics, battery management,
  and separately validated LTE/GNSS modules.

Backend
  Node.js with Express, PostgreSQL, and Prisma. The backend owns incident
  lifecycle, authentication, delivery orchestration, acknowledgement state,
  and audit records.

AI services
  Python services separated from the incident API. Start with recorded,
  authorized data and measurable evaluation.

Notifications and storage
  A push provider such as Firebase Cloud Messaging may support app delivery.
  Private object storage holds evidence media. Push receipt is not recipient
  acknowledgement.

2. CORE DATA MODEL
------------------

User
  id, account status, consent settings, language, created_at

Device
  id, user_id, hardware revision, firmware version, public key reference,
  last_seen, status

EmergencyContact
  id, user_id, contact details, priority, verification status

Incident
  id, source type, source ID, severity, status, created_at, location reference

LocationFix
  incident ID, latitude, longitude, accuracy, timestamp, source, age

DeliveryAttempt
  incident ID, channel, destination, attempt time, result, provider reference

Acknowledgement
  incident ID, actor, time, and acknowledgement type

Camera
  id, owner, authorization record, location, coverage geometry, status

CameraEvent
  id, camera ID, event type, confidence, event time, evidence reference,
  review status

EvidenceObject
  id, incident ID, storage key, hash algorithm, digest, metadata, retention date

AuditEvent
  actor, action, target, time, outcome, and immutable event reference

3. ILLUSTRATIVE API RESPONSIBILITIES
------------------------------------

POST /api/v1/incidents
  Create an incident from an authenticated app or device.

GET /api/v1/incidents/{id}
  Retrieve permitted incident status and details.

POST /api/v1/incidents/{id}/acknowledgements
  Record a human or authorized service acknowledgement.

POST /api/v1/devices/{id}/events
  Ingest a wearable event.

POST /api/v1/camera-events
  Ingest an authorized camera candidate event.

POST /api/v1/delivery-attempts
  Record a channel attempt and provider result.

POST /api/v1/evidence/manifest
  Register evidence metadata and its integrity digest.

GET /api/v1/nearby-alerts
  Return relevant and permitted nearby warnings.

Every endpoint requires authentication, validation, authorization, rate
limiting, idempotency handling, and versioning. The final contracts must be
defined only after threat modelling and operational review.

4. FIRMWARE MODULES
--------------------

SOS manager
  Button debounce, long-press handling, cancellation, and incident creation.

System state manager
  Boot, normal, emergency, low-battery, offline, and recovery states.

BLE service
  Secure pairing, GATT characteristics, message framing, and reconnects.

Cellular manager
  Modem power, SIM status, registration, APN, retries, and response parsing.

GNSS manager
  Fix acquisition, coordinate quality, time, and stale-location detection.

Offline queue
  Persistent writes, sequence numbers, retry schedule, and duplicate
  suppression.

Power, haptics, security, and diagnostics managers
  Sleep modes, rail switching, feedback patterns, key handling, watchdogs,
  fault codes, reset reasons, and engineering logs.

5. AI DEVELOPMENT PLAN
-----------------------

Personal safety AI may investigate audio or motion signals, but these signals
are contextual and cannot reliably infer assault or intent. On-device
processing is preferred when practical; data upload must follow the selected
user policy.

CCTV development should start with authorized recorded data, person detection,
and anonymous tracking. Add pose or temporal behaviour models only after
baseline quality is measured. Evaluation should include precision, recall,
false alerts per camera-hour, missed-event rate, latency, calibration, and
coverage across relevant conditions.

Every production candidate needs a human review path and a process for
recording false positives and missed events.

6. POWER AND BATTERY VALIDATION
-------------------------------

The power subsystem includes a protected Li-Po cell, charger, protection,
temperature sensing, fuel gauge, low-noise logic rail, dedicated modem rail,
load switches, brownout detection, watchdog, and safe shutdown.

Measurements should cover:

* 24-hour standby current.
* Connected BLE current and reconnect cost.
* GNSS time-to-first-fix and energy per fix.
* LTE registration, transmission peak current, and energy per SOS.
* Satellite attempt energy where applicable.
* Haptic energy and motor temperature.
* Battery life under strong and weak network conditions.

7. DELIVERY ROADMAP
-------------------

Stage 1 - Android manual SOS
  Account, contacts, permissions, location, local incident record, and clear
  status language.

Stage 2 - BLE wristband
  Pairing, SOS button, haptics, status, battery, and offline queue.

Stage 3 - Backend reliability
  Authenticated incident API, idempotent retries, delivery states,
  acknowledgements, and audit events.

Stage 4 - Independent device communication
  Validate LTE/GNSS modules, antenna, power, coverage, and firmware recovery.

Stage 5 - Evidence and authorized analytics
  Implement protected evidence handling and a recorded CCTV prototype with
  human review.

Stage 6 - Controlled operational pilot
  Complete legal, security, privacy, hardware, agency, and operational review
  before any real-world pilot.

Stage 7 - Scale
  Expand only after reliability, safety, false-alert burden, privacy controls,
  and support operations are demonstrated.

8. DEFINITION OF DONE FOR THE CONCEPT
--------------------------------------

The concept is ready for implementation planning when:

* Incident states and acknowledgement semantics are agreed.
* Offline queue and retry behaviour are testable.
* Hardware and communication assumptions are measured rather than assumed.
* API authorization and idempotency rules are documented.
* AI evaluation data and human review controls exist.
* Evidence retention, consent, and access policies are approved.
* Regulatory and emergency-service dependencies have named owners.
